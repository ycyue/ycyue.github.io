刚开始学习软件测试时，很多人知道要写测试用例，却不知道面对一句需求该从哪里下手。要么只写“输入正确账号可以登录”这种正常情况，要么列了很多测试点，却没有写清操作步骤和预期结果。

写测试用例的核心并不复杂：

> 把需求拆成可以执行、可以观察、可以判断结果的检查项。

一条完整的测试用例，需要回答四个问题：**测试什么、在什么条件下测试、怎么操作、什么结果才算正确。**

## 一、测试用例是什么

测试用例是为了验证某个功能或业务规则而设计的一组条件、步骤、数据和预期结果。

例如需求是：

> 已注册用户输入正确的手机号和密码后，可以成功登录。

“测试登录功能”只是一个笼统的测试任务，不是一条可以直接执行的用例。把它写成下面这样，执行者才知道具体怎么测：

| 字段 | 内容 |
| --- | --- |
| 用例编号 | LOGIN_001 |
| 用例标题 | 使用正确手机号和密码登录成功 |
| 前置条件 | 测试账号已注册且未被禁用 |
| 测试数据 | 手机号：13800000000；密码：Abc123456 |
| 操作步骤 | 1. 打开登录页；2. 输入手机号和密码；3. 点击“登录” |
| 预期结果 | 登录成功，进入首页，并显示当前用户信息 |

好的测试用例应该让另一个没有参与设计的人也能照着执行，并对结果作出相同判断。

## 二、一条测试用例通常包含哪些字段

实际公司的模板会有差异，但常用字段基本相同：

| 字段 | 作用 |
| --- | --- |
| 用例编号 | 唯一标识用例，例如 `LOGIN_001` |
| 所属模块 | 表明用例属于登录、注册或购物车等模块 |
| 用例标题 | 用一句话说明测试条件和预期行为 |
| 优先级 | 表示用例的重要程度，常用 P0、P1、P2 |
| 前置条件 | 执行前必须满足的账号、数据和环境条件 |
| 测试数据 | 本次测试实际使用的输入值 |
| 操作步骤 | 按顺序写出可执行的操作 |
| 预期结果 | 每一步或最终应该出现的可观察结果 |
| 实际结果 | 执行测试后记录系统的真实表现 |
| 执行结果 | Pass、Fail 或 Blocked |

初学时不需要追求字段越多越好。最重要的是标题、前置条件、步骤、数据和预期结果都明确。

## 三、从需求到测试用例的四个步骤

### 第一步：读懂需求，找出规则

不要看到页面就立刻开始写用例。先圈出需求中的对象、条件、限制、动作和结果。

例如：

> 用户使用中国大陆手机号登录。手机号必须为 11 位；密码为 8～20 个字符；连续输错 5 次后，账号锁定 30 分钟。

可以拆出四条规则：

1. 手机号只能使用规定格式；
2. 手机号长度必须为 11 位；
3. 密码长度为 8～20 个字符；
4. 密码连续错误 5 次会触发账号锁定，30 分钟后解除。

如果需求中有不明确的地方，例如“连续输错”是否跨设备累计、锁定期间输入正确密码是否允许登录，就应该先向产品或需求负责人确认，而不是自己猜测。

### 第二步：把每条规则拆成测试点

初学阶段可以使用“正、反、边、空、异”检查是否遗漏：

- **正**：符合规则的正常情况；
- **反**：不符合规则的错误情况；
- **边**：刚好位于限制边界及边界两侧的情况；
- **空**：必填项为空、只输入空格或未选择；
- **异**：网络中断、重复点击、服务异常等特殊情况。

继续以上面的登录需求为例，可以得到这些测试点：

- 正确手机号和正确密码；
- 正确手机号和错误密码；
- 未注册手机号；
- 手机号为空、密码为空、两者都为空；
- 手机号为 10 位、11 位、12 位；
- 密码为 7 位、8 位、20 位、21 位；
- 手机号包含字母、空格或特殊字符；
- 密码连续错误第 4 次、第 5 次和锁定后的登录行为；
- 锁定 30 分钟前后分别尝试登录；
- 点击登录时断网；
- 快速连续点击登录按钮。

### 第三步：选择合适的设计方法

“正、反、边、空、异”适合帮助新手建立检查意识，但要系统设计用例，还需要使用正式方法。

#### 1. 等价类划分

把大量输入划分为具有相同行为的类别，每类选择有代表性的数据，不需要穷举所有值。

以“密码长度为 8～20 位”为例：

- 有效等价类：8～20 位；
- 无效等价类：少于 8 位；
- 无效等价类：多于 20 位；
- 无效等价类：空值。

#### 2. 边界值分析

错误最容易出现在范围边缘，所以要检查边界本身和边界相邻值。

密码长度为 8～20 位时，重点数据是：

| 长度 | 预期结果 |
| ---: | --- |
| 7 | 提示密码长度不合法 |
| 8 | 允许输入并提交 |
| 9 | 允许输入并提交 |
| 19 | 允许输入并提交 |
| 20 | 允许输入并提交 |
| 21 | 提示密码长度不合法 |

也可以记成“边界内、边界上、边界外”。

#### 3. 场景法

按用户完成业务的过程设计用例，既覆盖主流程，也覆盖中断和失败流程。

登录的主流程是“输入账号密码—校验成功—进入首页”；异常流程可能包括密码错误、账号锁定、验证码失效和网络中断。

#### 4. 判定表

当多个条件组合会产生不同结果时，可以先列条件组合，再转成用例。例如“账号是否存在、密码是否正确、账号是否锁定”三个条件同时影响登录结果，使用判定表比凭感觉组合更不容易遗漏。

### 第四步：把测试点写成可执行用例

测试点只说明“要测什么”，测试用例还必须说明“怎么测”和“如何判断”。下面是一组简化后的登录用例：

| 编号 | 用例标题 | 前置条件 | 测试数据 | 操作步骤 | 预期结果 |
| --- | --- | --- | --- | --- | --- |
| LOGIN_001 | 正确手机号和密码登录成功 | 账号已注册且正常 | 正确手机号、正确密码 | 输入数据并点击登录 | 登录成功并进入首页 |
| LOGIN_002 | 正确手机号配错误密码登录失败 | 账号已注册且正常 | 正确手机号、错误密码 | 输入数据并点击登录 | 登录失败，提示账号或密码错误，不进入首页 |
| LOGIN_003 | 手机号为空时不能登录 | 无 | 手机号为空、有效密码 | 输入密码并点击登录 | 提示手机号不能为空，不发送登录请求 |
| LOGIN_004 | 10 位手机号不能登录 | 无 | 10 位数字、有效密码 | 输入数据并点击登录 | 提示手机号格式错误 |
| LOGIN_005 | 密码长度刚好为 8 位 | 存在密码为 8 位的账号 | 正确手机号、8 位正确密码 | 输入数据并点击登录 | 登录成功并进入首页 |
| LOGIN_006 | 连续第 5 次输错密码后锁定账号 | 账号已连续输错 4 次 | 正确手机号、错误密码 | 再次输入错误密码并登录 | 登录失败，提示账号已锁定 30 分钟 |
| LOGIN_007 | 锁定期间输入正确密码仍不能登录 | 账号处于锁定状态 | 正确手机号、正确密码 | 输入数据并点击登录 | 登录失败，提示账号仍处于锁定状态 |
| LOGIN_008 | 网络中断时提交登录 | 设备已断网 | 正确手机号、正确密码 | 输入数据并点击登录 | 页面给出网络异常提示，不出现无限加载或崩溃 |

## 四、怎样写好用例标题、步骤和预期结果

### 标题要包含条件和结果

不推荐：

> 测试登录功能

推荐：

> 已注册用户使用正确手机号和密码登录成功

标题应该让人不打开详情，也能知道这条用例在验证什么。

### 步骤要具体，但不要写无意义动作

“正常操作并登录”太模糊；“启动电脑、打开浏览器”在大多数网页测试中又过于琐碎。

步骤应该从当前前置条件之后开始，并写清关键操作：

1. 打开登录页；
2. 在手机号输入框输入指定号码；
3. 在密码输入框输入指定密码；
4. 点击“登录”。

### 预期结果必须可观察、可判断

不推荐：

> 系统正常。

推荐：

> 登录成功，页面跳转到首页；右上角显示当前用户昵称；刷新页面后仍保持登录状态。

“正常”“正确”“没有问题”都缺少判断标准。预期结果应描述页面、数据、提示、状态或请求发生了什么变化。

## 五、写完以后怎样检查

可以从以下几个方面做一次自查：

1. **需求覆盖**：每条明确的业务规则是否至少有一条用例验证；
2. **正反覆盖**：既有成功流程，也有失败流程；
3. **边界覆盖**：长度、数量、时间和金额等限制是否检查了边界内外；
4. **步骤可执行**：其他人是否能在不询问你的情况下完成操作；
5. **结果可判断**：Pass 和 Fail 是否有清楚标准；
6. **用例独立**：执行顺序改变后，是否仍能得到稳定结果；
7. **数据明确**：手机号、账号状态和次数等数据是否写清楚。

用例并不是越多越好。大量重复用例会提高维护成本，却不一定增加有效覆盖。应该优先保证核心业务、常用流程、高风险功能和历史缺陷得到充分验证。

## 六、初学者常见错误

### 只测试正常流程

真实缺陷往往出现在错误输入、边界条件、状态切换和异常操作中。每看到一条规则，都要问一句：“不满足它会怎样？”

### 把测试点当成完整用例

“密码为空”“手机号错误”可以作为测试点，但缺少前置条件、数据、步骤和预期结果时，还不能直接交给别人执行。

### 一条用例验证太多事情

如果一条用例同时验证手机号格式、密码边界、账号锁定和网络异常，失败后很难判断是哪条规则出了问题。一般让一条用例有一个明确的主要验证目标。

### 预期结果照抄需求

需求写“登录成功”，用例也只写“登录成功”，仍然不够具体。需要说明跳转页面、用户状态、提示信息以及必要的数据变化。

### 不记录测试数据

只写“输入正确账号”会导致用例无法复现。应该写明账号本身，或者写清可以从哪里取得满足条件的测试账号。

## 七、适合新手的练习方法

可以依次选择登录、注册、搜索、购物车和订单提交五个常见模块练习。每个模块都按同一个过程完成：

1. 写出一段简短需求；
2. 圈出其中的业务规则；
3. 使用等价类、边界值和场景法列测试点；
4. 把测试点整理成正式用例表；
5. 用需求逐条检查覆盖情况；
6. 让别人只看用例执行一次，找出不清楚的地方。

写测试用例不是套模板，而是把需求转化为可验证的规则。真正需要掌握的流程是：

> **读需求 → 拆规则 → 找测试点 → 选设计方法 → 写步骤和预期结果 → 检查覆盖。**

先把一个登录模块写清楚，再逐步扩展到注册、购物车和订单流程，比一次背完所有测试方法更有效。
