刚开始学习软件测试时，很容易被大量英文术语弄得混乱：

- 测试计划、测试分析、测试设计到底有什么区别？
- Test Basis、Testware、Test Case 分别是什么？
- 单元测试、功能测试、黑盒测试是不是同一层级的概念？
- 测试人员到底是在“写用例”，还是在执行测试？

这些问题其实可以放进三张互相连接的地图中：

| 地图 | 主要回答的问题 | 关键概念 |
| --- | --- | --- |
| 测试过程 | 一轮测试怎样开展？ | Planning、Analysis、Design、Execution…… |
| 测试依据与工作产品 | 为什么这样测？留下了什么证据？ | Test Basis、Testware、Traceability |
| 测试级别与分类 | 测试对象处在哪一层？采用什么目标和方式？ | Component、System、Functional、Black-box…… |

本文根据软件测试基础学习对话整理，并以 [ISTQB CTFL v4.0.1 官方大纲](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf) 为术语和流程的校对依据。

## 一、先理解：软件测试不是“打开网页随便点”

在真实项目中，测试人员要做的事情远不止发现 Bug。通常还包括：

1. 理解需求和业务规则；
2. 判断哪些内容需要测试；
3. 设计测试条件、测试用例和测试数据；
4. 准备环境、账号和依赖服务；
5. 执行测试并记录结果；
6. 分析异常，提交清晰的缺陷报告；
7. 根据风险、覆盖情况和剩余缺陷，向团队报告质量状态。

所以，软件测试是一组有目标、有依据、有过程、有产出的活动。

## 二、Test Process：一轮测试怎样开展

ISTQB CTFL v4.0.1 将一个典型测试过程概括为七组主要活动：

1. Test Planning：测试计划；
2. Test Monitoring and Control：测试监控与控制；
3. Test Analysis：测试分析；
4. Test Design：测试设计；
5. Test Implementation：测试实现；
6. Test Execution：测试执行；
7. Test Completion：测试完成。

它们看起来有先后顺序，但不应该理解成固定的瀑布流水线。在真实项目中，这些活动经常迭代或并行进行，并且需要根据项目上下文进行裁剪。

### 1. Test Planning：测试计划

测试计划首先要回答：

> 这次测试要达到什么目标？在当前时间、人员和环境约束下，准备怎样完成？

以电商网站新增登录功能为例，测试计划需要考虑：

- 测试范围是什么：登录页面、登录接口，还是完整认证流程？
- 哪些风险最高：账户锁定、身份认证、密码安全？
- 什么时候上线，测试时间有多少？
- 有多少测试人员？
- 测试环境和测试账号是否已经准备好？
- 本轮做功能测试、接口测试、兼容性测试还是性能测试？
- 什么条件下可以结束测试并给出发布建议？

因此，Planning 不是“开始写测试用例”，而是确定目标、范围、策略、资源、时间、风险和完成标准。

### 2. Test Monitoring and Test Control：测试监控与控制

这两个概念经常放在一起，但含义不同。

**Test Monitoring（测试监控）**是持续收集测试状态，并把实际进展与计划进行比较。例如：

- 计划执行 100 条用例，实际执行了多少？
- 通过、失败和阻塞分别是多少？
- 高风险功能是否已经覆盖？
- 哪些问题影响了测试进度？

**Test Control（测试控制）**是在发现偏差后采取行动。例如：

- 优先执行高风险用例；
- 暂缓低风险的兼容性测试；
- 调整测试范围或测试顺序；
- 增加测试人员；
- 协调开发解除环境或数据阻塞；
- 修改测试计划和完成标准。

可以这样记：

| 概念 | 核心问题 |
| --- | --- |
| Monitoring | 现在进行得怎么样？ |
| Control | 根据当前情况应该采取什么措施？ |

### 3. Test Analysis：测试分析

Test Analysis 回答的是：

> What to test？——测什么？

测试分析要根据 Test Basis（测试依据）识别可测试的特性、测试条件和相关风险，还要检查测试依据和被测对象本身是否存在缺陷，以及是否具备可测试性。

假设需求是：

> 用户连续输入错误密码 5 次后，账户锁定 30 分钟。

测试分析阶段不会马上写完整步骤，而是先提出问题：

- 什么叫“连续错误”？
- 登录成功一次后，错误次数是否清零？
- 锁定期间输入正确密码能否登录？
- 30 分钟从第 5 次错误开始计算吗？
- 锁定后再次输入密码，会不会重新计算时间？
- 其他设备能否登录这个已锁定账户？

然后把需求拆成测试条件：

- 正常登录；
- 错误密码；
- 连续错误次数；
- 第 5 次错误；
- 账户锁定；
- 锁定持续时间；
- 锁定解除；
- 登录成功后的页面跳转。

这些“需要测试的方面”就是 Test Conditions（测试条件）。

### 4. Test Design：测试设计

Test Design 回答的是：

> How to test？——怎么测？

测试分析得到“测试连续失败 5 次后锁定”，测试设计则要把它展开成具体输入、步骤和预期结果：

- 第 4 次输入错误密码：不应锁定；
- 第 5 次输入错误密码：应触发锁定；
- 锁定后输入正确密码：仍不能登录；
- 锁定未满 30 分钟：不允许登录；
- 锁定满 30 分钟：允许按照正常规则登录。

这时才开始形成具体测试用例。例如：

| 字段 | 内容 |
| --- | --- |
| 用例名称 | 连续错误 5 次后账户锁定 |
| 前置条件 | 账户正常，当前错误次数为 0 |
| 操作步骤 | 输入正确手机号，连续 5 次输入错误密码，再次尝试登录 |
| 预期结果 | 前 4 次提示密码错误；第 5 次后账户被锁定；后续登录提示账户处于锁定状态 |

等价类、边界值、判定表和状态迁移等测试设计技术，都是帮助测试人员完成“测什么”和“怎么测”的工具。

### 5. Test Implementation：测试实现

这里的 Implementation 不是开发人员实现业务功能，而是：

> 把已经设计好的测试准备成真正可以执行的状态。

可能需要准备：

- 测试账号和密码；
- 测试数据；
- 数据库初始状态；
- 测试环境；
- 浏览器或移动设备；
- 接口地址；
- 测试脚本；
- 测试套件；
- 测试执行顺序。

例如，要验证“已经错误 4 次，第 5 次触发锁定”，就可能需要把测试账号的失败次数准备为 4。测试数据和测试环境没有准备好，后面的执行结果就不可靠。

### 6. Test Execution：测试执行

Test Execution 才是大家通常理解的“开始测试”：

1. 按照测试计划和执行安排运行测试；
2. 将实际结果与预期结果比较；
3. 记录测试结果；
4. 分析异常的可能原因；
5. 确认后提交缺陷报告。

例如：

- 预期结果：连续错误 5 次后账户锁定；
- 实际结果：连续错误 5 次后仍然可以使用正确密码登录。

这说明 Expected Result 不等于 Actual Result，出现了异常。

但要注意：

> 出现异常，不等于已经证明是产品 Bug。

测试失败还可能是由以下原因造成的：

- 测试用例写错；
- 测试数据不正确；
- 数据库状态不符合前置条件；
- 测试环境异常；
- 网络故障；
- 需求理解错误；
- 产品确实存在缺陷。

因此，测试人员需要先分析异常，再决定是否提交 Defect Report（缺陷报告）。

### 7. Test Completion：测试完成

测试完成通常发生在版本发布、迭代结束或某个测试级别完成等里程碑，而不是“所有用例跑完就下班”。

收尾阶段可能需要：

- 汇总用例执行情况；
- 统计通过、失败、阻塞和缺陷数据；
- 评估未解决缺陷和剩余风险；
- 判断是否达到 Exit Criteria；
- 归档仍有价值的测试工作产品；
- 记录经验教训和改进项；
- 输出 Test Completion Report（测试完成报告）。

测试完成报告不只是列出“通过了多少条”，还应该帮助相关人员理解当前质量状态、测试覆盖、未解决风险和是否适合发布。

### 8. 七个活动不是机械流水线

现实中经常出现这样的循环：

分析登录需求
↓
设计测试用例
↓
执行测试
↓
发现需求存在歧义
↓
重新分析需求
↓
增加测试条件和用例
↓
继续执行测试

所以，Test Process 是一组可以迭代和并行开展的活动模型，而不是必须严格执行一次的七步生产线。

## 三、Test Basis、Test Object 与 Testware

### 1. Test Basis：我凭什么判断软件应该怎样工作

Test Basis 可以理解为：

> 用来分析应该测试什么、判断预期结果应该是什么的信息来源。

常见的测试依据包括：

- 产品需求文档；
- User Story；
- Acceptance Criteria；
- 业务规则；
- 接口文档；
- 设计说明；
- 法规和行业要求；
- 风险分析结果。

例如需求规定：

> REQ-001：用户连续输入错误密码 5 次后，账户锁定 30 分钟。

那么“连续 4 次不锁定”“连续 5 次锁定”“锁定 29 分钟不能登录”“锁定 30 分钟后恢复登录”等测试，都应该能够追溯到 REQ-001，而不是测试人员凭感觉创造出来的。

### 2. Test Object：我到底在测试谁

Test Object 是被测试的对象，例如：

- 一个函数；
- 一个类；
- 登录页面；
- 登录接口；
- 订单模块；
- 整个商城系统；
- 商城与支付平台之间的交互。

Test Basis 和 Test Object 的区别可以这样记：

| 概念 | 记忆方式 | 示例 |
| --- | --- | --- |
| Test Object | 我测谁？ | 登录页面、登录接口、认证系统 |
| Test Basis | 我凭什么判断它对不对？ | 登录需求、接口文档、验收标准 |

需求文档本身也可能有缺陷，例如“密码长度为 8～20 位”没有说明按字符数还是字节数计算，或者“多次输错后锁定”没有说明到底是多少次。

因此，Test Analysis 不只是从需求中找测试点，也要识别测试依据中的歧义、不完整和不一致。需求评审属于静态测试的重要场景。

### 3. Testware：测试活动产生的工作产品

Testware 不是“测试用例”的同义词，而是测试活动中产生和使用的各种工作产品的总称。不同公司对这些工作产品的名称、格式和管理方式可能不同。

| 测试活动 | 典型工作产品 |
| --- | --- |
| Test Planning | 测试计划、测试日程、风险登记表、进入和退出标准 |
| Monitoring and Control | 测试进度报告、控制措施、风险信息 |
| Test Analysis | 测试条件、测试依据缺陷报告 |
| Test Design | 测试用例、覆盖项、测试数据需求、测试环境需求 |
| Test Implementation | 测试过程、手工或自动化脚本、测试套件、测试数据、测试环境项 |
| Test Execution | 测试日志、缺陷报告 |
| Test Completion | 测试完成报告、经验教训、改进项、变更请求 |

所以，测试用例只是 Testware 的一种。

### 4. Test Condition、Test Case 和 Test Data

这三个概念非常容易混淆：

| 概念 | 回答的问题 | 登录示例 |
| --- | --- | --- |
| Test Condition | 测试什么？ | 测试连续错误次数和账户锁定 |
| Test Case | 具体怎么验证？ | 连续输入错误密码 4 次、5 次，再尝试登录 |
| Test Data | 实际使用哪些数据？ | 正确手机号、错误密码、错误次数为 4 的账号 |

一个测试点通常还不能直接执行。只有补充了前置条件、具体步骤、测试数据和可判断的预期结果后，才形成可执行的测试用例。

## 四、Traceability：把需求、用例、结果和 Bug 连起来

Traceability 的中文通常译为可追踪性或可追溯性。它要解决的问题是：

> 一条测试用例在验证哪个需求？一个失败结果影响哪个风险？一个 Bug 又对应哪个测试？

可以建立这样的关系链：

需求 REQ-001
↓
测试条件：验证连续错误次数
↓
测试用例 TC-001、TC-002
↓
测试结果：TC-002 FAILED
↓
缺陷 BUG-027

### 1. 为什么需要 Traceability

它至少有四个作用：

1. **检查需求覆盖**：知道每条需求是否有测试用例；
2. **支持变更影响分析**：需求变化后，快速找到需要修改和重新执行的用例；
3. **帮助解释测试结果**：从需求可以追到测试结果和缺陷状态；
4. **支持进度和质量报告**：让项目成员知道哪些需求已覆盖、哪些风险仍未验证。

例如，产品经理把“锁定 30 分钟”改成“锁定 15 分钟”。如果已经维护了追踪关系，就可以快速定位相关测试用例并执行回归测试，而不必在几百条用例中逐条寻找。

### 2. 双向可追踪

追踪关系最好是双向的：

- 从需求向下追到测试用例、结果和缺陷；
- 从测试用例向上追到它所对应的需求。

这样，当你看到一条长期无人维护的测试用例时，可以回答：

> 这条用例为什么存在？它到底是在验证哪个业务要求？

### 3. Coverage：必须先说明覆盖什么

假设共有 10 条需求，其中 8 条已经有测试用例：

Coverage = 8 ÷ 10 × 100% = 80%

这只能说明“需求覆盖率”是 80%，不能说明发现了 80% 的 Bug，更不能证明软件没有缺陷。

说“覆盖率达到 90%”是不完整的，必须进一步说明：

- 需求覆盖率？
- 语句覆盖率？
- 分支覆盖率？
- 接口覆盖率？
- 测试场景覆盖率？

没有明确覆盖对象，单独的百分比没有足够的信息量。

## 五、Test Levels：测试对象处在哪一层

Test Level 主要回答：

> 当前是在测试一个组件、组件之间的交互、完整系统、系统之间的交互，还是业务是否可以接受？

ISTQB CTFL v4.0.1 描述了五个常见测试级别：

### 1. Component Testing：组件测试 / 单元测试

测试单独的组件，通常在隔离条件下进行，也经常使用单元测试框架。

例如商城中有一个计算折扣的函数：

    calculate_discount(price, vip)

只验证这个函数在不同输入下返回的结果，而不打开完整商城、不登录、不创建订单，这属于 Component Testing。

它通常主要由开发人员完成，但测开或测试人员也可能参与编写和维护。

### 2. Component Integration Testing：组件集成测试

测试组件之间的接口和交互。

例如：

订单模块
↓
库存模块

订单创建成功，但库存没有扣减，可能就是组件之间的数据传递或接口契约不一致。

即使订单模块单独测试通过、库存模块单独测试也通过，也不能推出两个模块连接后一定正确。

### 3. System Testing：系统测试

把完整系统作为一个整体，测试它的整体行为和能力。

例如完整执行：

注册
↓
登录
↓
搜索商品
↓
加入购物车
↓
提交订单
↓
支付
↓
查看订单

系统测试可以包含端到端功能测试，也可以包含性能、兼容性、易用性和安全等非功能质量特性。

### 4. System Integration Testing：系统集成测试

测试被测系统与其他系统或外部服务之间的接口和交互。

例如：

商城
↓
调用支付平台
↓
支付平台回调商城
↓
商城订单变为“已支付”

这里关注的不是商城内部订单模块和库存模块，而是商城与支付平台、短信平台、物流系统或地图服务之间的系统级交互。

### 5. Acceptance Testing：验收测试

验收测试更关注：

> 系统是否满足用户的业务需要，是否已经具备投入使用的准备程度？

一个仓库管理系统可能在技术上运行正常，但如果真实仓库员工无法按照实际流程完成“扫码、检查批次、登记仓位、打印标签、确认入库”，仍然可能无法通过业务验收。

常见形式包括：

- User Acceptance Testing（UAT，用户验收测试）；
- Operational Acceptance Testing（运行验收测试）；
- Contractual Acceptance Testing（合同验收测试）；
- Regulatory Acceptance Testing（法规验收测试）；
- Alpha Testing；
- Beta Testing。

UAT 只是 Acceptance Testing 的一种，不等于全部验收测试。

## 六、不要把 Test Level、Test Type 和 Test Technique 混在一起

这是初学者最容易犯的概念错误之一。

| 维度 | 主要回答的问题 | 示例 |
| --- | --- | --- |
| Test Level | 在软件的哪一层测试？ | Component、System、Acceptance |
| Test Type | 关注什么功能、质量特征或规格/结构依据？ | Functional、Non-functional、Black-box、White-box |
| 变更相关测试 | 修改或修复之后要验证什么？ | Confirmation、Regression |
| Test Technique | 根据什么信息设计测试？ | 等价类、边界值、判定表、状态迁移、经验法 |

在 ISTQB CTFL v4.0.1 中，Functional、Non-functional、Black-box 和 White-box 都在 Test Types 部分被讨论；而黑盒、白盒又在 Test Techniques 章节中展开。学习时不必被术语层级卡住，最重要的是把“在哪一层”“关注什么”“依据什么设计”分开。

### 1. Functional Testing：测功能是否正确

功能测试检查系统应该做什么，例如：

- 正确账号密码能够登录；
- 错误密码给出提示；
- 连续错误 5 次后锁定；
- 订单支付成功后状态更新。

### 2. Non-functional Testing：测系统表现得怎么样

非功能测试关注“系统怎样工作”，例如：

- 性能效率；
- 兼容性；
- 易用性；
- 可靠性；
- 安全性；
- 可维护性；
- 可移植性；
- 安全保障性。

功能测试和非功能测试都可以出现在不同的测试级别。

### 3. Confirmation Testing 与 Regression Testing

修复缺陷或修改功能后，通常要区分两种测试：

**Confirmation Testing（确认测试）**：确认原来的缺陷已经被修复。  
例如重新执行之前失败的“连续错误 5 次后锁定”用例。

**Regression Testing（回归测试）**：确认这次修改没有对其他部分造成不良影响。  
例如修复登录锁定逻辑后，重新检查正常登录、密码重置、短信验证码和其他认证流程。

确认测试只关注原缺陷是否修复；回归测试关注修改是否引入新的问题。两者都可以发生在不同测试级别。

### 4. Black-box 与 White-box

**Black-box Testing（黑盒测试）**根据需求、规格说明和外部可观察行为设计测试，不依赖被测对象的内部实现。

例如只根据“年龄必须为 18～60 岁”选择 17、18、19、60、61 等数据，而不查看代码。

**White-box Testing（白盒测试）**根据代码、结构、控制流或数据流设计测试，关注内部结构是否被覆盖。

例如针对下面的判断，要求 True 分支和 False 分支都被执行：

    if age >= 18:
        return "adult"
    return "minor"

黑盒与白盒不是测试级别。下面这些说法都不严谨：

- 黑盒测试就是系统测试；
- 白盒测试就是单元测试；
- 单元测试一定只能使用白盒测试。

更准确的理解是：单元测试经常使用白盒技术，系统测试经常使用黑盒技术，但这些只是常见组合，不是概念上的等号。

## 七、用一个商城登录项目把所有概念串起来

假设需求是：

> 用户可以使用手机号和密码登录；密码错误时提示；连续错误 5 次后锁定账户 30 分钟；登录成功后进入首页。

可以按下面的链路开展测试：

1. **Test Basis**：登录需求、验收标准、接口文档和业务规则；
2. **Test Object**：登录页面、登录接口和认证模块；
3. **Test Analysis**：识别正常登录、错误密码、错误次数、锁定和解除锁定等测试条件；
4. **Test Design**：选择边界值和状态转换，设计具体测试用例；
5. **Test Implementation**：准备测试账号、数据库状态、环境和测试数据；
6. **Test Execution**：执行用例，记录实际结果并分析异常；
7. **Defect Report**：确认“连续 5 次错误后仍可登录”是产品缺陷并提交报告；
8. **Traceability**：把需求、测试条件、用例、结果和缺陷关联起来；
9. **Confirmation Testing**：开发修复后重新验证原缺陷；
10. **Regression Testing**：确认修复没有影响正常登录、密码重置等其他功能；
11. **Test Completion**：汇总结果、剩余风险和是否达到发布标准。

如果从测试级别看：

| 场景 | 测试级别 | 可能的测试类型或方式 |
| --- | --- | --- |
| 单独测试密码校验函数 | Component Testing | Functional，可能使用 White-box |
| 测试登录模块与用户数据库的交互 | Component Integration Testing | Functional |
| 测试整个商城登录和首页跳转 | System Testing | Functional、Black-box |
| 测试商城与短信平台的交互 | System Integration Testing | Functional、接口交互 |
| 业务人员模拟真实工作并决定能否上线 | Acceptance Testing | UAT、业务场景 |

这就是为什么一次测试活动可以同时拥有多个标签，而不能把单元测试、功能测试、黑盒测试当成同一条线上的概念。

## 八、初学者真正需要记住的内容

可以把整篇笔记压缩成下面几句话：

1. **Test Planning**：确定目标、范围、策略、资源和完成标准；
2. **Test Monitoring**：持续比较实际进展与计划；
3. **Test Control**：根据偏差采取调整措施；
4. **Test Analysis**：识别测试条件，回答“测什么”；
5. **Test Design**：形成测试用例和测试数据，回答“怎么测”；
6. **Test Implementation**：准备工作产品、环境和执行顺序；
7. **Test Execution**：执行测试、记录结果、分析异常和报告缺陷；
8. **Test Completion**：总结结果、剩余风险、经验和改进项；
9. **Test Basis**：测试判断的依据；
10. **Testware**：测试活动产生的全部工作产品；
11. **Traceability**：把需求、测试、结果和缺陷连接起来；
12. **Test Level**：说明测试对象处在哪一层；
13. **Test Type / Technique**：说明关注什么以及依据什么设计；
14. **Confirmation Testing** 验证原缺陷是否修复，**Regression Testing** 验证修改是否引入新问题。

当你拿到一个新功能时，可以按照这条实践链行动：

> 找到测试依据 → 明确测试对象 → 拆出测试条件 → 设计测试用例和数据 → 准备环境 → 执行并记录 → 分析异常 → 提交缺陷 → 维护追踪关系 → 完成回归和总结。

这条链路比单独背诵几十个英文术语更重要。因为真实测试工作，本质上就是围绕这条链路不断产生证据、发现风险和提供质量信息。
